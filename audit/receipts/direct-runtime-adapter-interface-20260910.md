## Interface A: entry and semantic state relation

Define an Amsterdam actual-call witness from the selected reference interpreter/block transition, with pre-call snapshot, post-transfer entry, actual owner/current_target, code address and code bytes, caller, origin, apparent value, transferred value, calldata, static flag, initial stack/memory/PC, transaction-original storage and trace/outcome. The witness must be derived from execution, not supplied as an assumed successful pinned path.

Relate it to MessageCall.Context at the same frame boundary. Require exact installed code, current_target equal the protected address, equal caller/calldata/apparent value, equal storage and account world under the chosen representation, and initial empty stack/memory/PC. Preserve original storage and warm access information where needed to calculate shadow cost, or explicitly choose a conservative shadow warm/original state and prove it cannot affect values. The semantic relation erases gas, refunds, access-list bookkeeping, trace instrumentation and reference-only state tracking; it preserves every field used by the existing postconditions. Prove balance/value transfer once at entry. Amsterdam debits then credits; pinned Θ credits then debits. They coincide with sufficient funds and no destination overflow; treat caller=target separately (final balance unchanged) rather than using a false intermediate equality. Funding/admission supplies those arithmetic premises. Do not silently map arbitrary missing sender accounts to funded callers.

For ordinary genuine target calls require transferred value = apparent value, as DirectGuarantees.Domain does. A STATICCALL has both zero. Outer delegated execution may issue such a call and is included. Executing the predeploy's bytes by DELEGATECALL/CALLCODE in another storage owner is outside the protected queue claim, not an excluded transaction. An actual call with owner=protected address but apparent/actual mismatch needs a separate generalized local statement or a proved invariant that this protected no-CALL runtime cannot produce that self-context; do not force ordinaryValue by definition.

## Interface B: successful trace to shadow execution

Proposed statement: for an actual successfully completed Amsterdam runtime trace t and related entry c0, construct gShadow, fuelShadow and c differing from c0 only in permitted erased/bookkeeping fields, with c.result = ok(created, world, gLeft, substate, true, output); the result world, output and runtime-log delta relate to the actual result. No equality of either initial or final gas is asserted.

Use induction over actual steps. For each allowed opcode, prove the gas-erased transition agrees whenever Amsterdam succeeds and the pinned resource guard succeeds. The proof is against the actual opcode semantics, including operand order, modular arithmetic, zero-padding and jump-target checking. These obligations are small but are not discharged just by seeing the same opcode names.

Calculate shadow legacy costs along that finite semantic trace, including memory expansion and SSTORE's 2300-gas sentry. Choose gShadow at least the cumulative cost plus a sentry margin, and construct Nat fuel from the exact pinned X/Xi/Theta decrement equations. Prove both cost and gShadow < 2^256 before converting to UInt256. Finiteness alone does not imply this word bound. Derive it from valid reference resource limits and a per-op legacy/reference cost bound, or from the already bounded safe runtime path. Do not assume the desired pinned execution as the cost certificate. No nested child wrapper is needed inside these runtimes, which simplifies the fuel recurrence. A sufficient-fuel/stability lemma must follow that recurrence, not use gas as Nat fuel.

Apply psubmit1_direct, pdrain1_direct and the RuntimeControl component of pcontrol1_direct to the constructed successful call and independently derived Domain. Transport their observations back through the state relation. The fee-safe bound, queue invariant and accounted budget remain history obligations, not adapter postconditions to assume.

## Interface C: exact log accounting

Represent a call's newly produced logs as entrySynthetic ++ runtimeDelta. At this genuine no-child runtime call, entrySynthetic is empty or the single reference EIP-7708 transfer LOG3 generated for nonzero transfer between distinct addresses; runtimeDelta is the exact ordered delta produced by runtime opcodes. Keep provenance/boundary information: do not globally remove all logs resembling transfer LOG3, since arbitrary outer code can emit similar data.

The existing AuthenticLog result gives runtimeDelta = [authentic LOG0] for a successful nonempty user append; getter and SYSTEM have runtimeDelta = []. Therefore preserve the original promise exactly: one LOG0 at the target, correct data and zero topics, with no other runtime logs. State separately that the full successful paid reference call may have two logs, entry LOG3 followed by that LOG0. A literal transport of the pinned raw logSeries append equality across the whole reference call is false. This is a concrete counterexample to full-log equality, not to the filtered/provenance adapter. SYSTEM zero value has no entry transfer LOG3, so its full log-preservation statement does transport.

## Interface D: REVERT and resource failure

For an actual explicit REVERT, replay the finite trace with sufficient shadow resources to the same REVERT data; both settled calls fail and restore frame world/log journal. Meter leftovers need not agree. For actual OOG, static-write failure or other exceptional halt, prove reference rollback directly from its snapshot/settlement. A high-shadow-gas replay may succeed where the real call ran out of gas; it must not be required to preserve that failure outcome. No gas-equality adapter can be used here.

Submission/control failure guarantees need only actual frame journal rollback, not a matching pinned resource failure. Underpayment/inhibition impossibility of reference success follows by contradiction through Interface B and existing success-necessity theorems. A successful child append later reverted by an ancestor remains a charged attempted occurrence but not a committed receipt/queue mutation. Maintain those two notions separately. OutOfFuel is solely a pinned proof-evaluation phenomenon and is eliminated by the constructive fuel witness.

Reference: [exception/revert settlement](https://github.com/ethereum/execution-specs/blob/0cc100eb190b64b23baba72dac0165652eaec252/src/ethereum/forks/amsterdam/vm/interpreter.py#L453). This avoids claiming equivalence of Amsterdam OOG and pinned OutOfGass/OutOfFuel.

## Interface E: SYSTEM success, independent of actual-success premise

Interface B alone proves safety only; using it to prove SYSTEM progress would assume the desired success. Prove a second direction for the bounded SYSTEM semantic path: construct the gas-erased path from exact code (or the pinned SystemProgress witness), bound its Amsterdam execution and state charges, then induct that each reference guard succeeds from the configured initial meter. Conclude actual success and use B for the existing functional postconditions.

The SYSTEM branch writes only controls 0,1,2,3. It executes either head write or head/tail reset, then excess and count writes: at most four SSTOREs, each control at most once. Queue record slots are read but never cleared. Thus at most four new-slot state charges, no more than 4 * 97,920 = 391,680 state gas at this pin; the configured 16 * 97,920 = 1,566,720 reservoir suffices without spill. Arbitrary starting control values do not increase that count. Establish this write-site/path lemma formally; it is source evidence here.

Deposit reads at most 64*6 record slots plus at most four control reads; Exit at most 16*3 plus four. Nonempty proposed migration calldata only selects inhibitor and does not introduce copying or a new loop. Maximum output is 64*184 = 11,776 bytes (Exit 1,088); prove a small additional padding bound for final MSTORE before using it in memory cost.

A conservative candidate resource envelope can be obtained from the existing bounded SYSTEM path: at most 8,502 execution steps, each non-storage base charge at most 10, at most 388 SLOADs charged <=2,100, and four SSTOREs charged <=12,100 execution gas, plus bounded memory expansion. Counting storage base twice is harmless. With a proved memory high-water <=12,288 bytes (384 words, expansion cost 1,440), this envelope is 949,660 execution gas, far below 30M. This number is a proposed arithmetic bound, NOT a proved Amsterdam gas receipt; the step-count interpretation and memory bound must be extracted/proved from the path, and call-dispatch overhead bounded separately. SSTORE sentries require a positive remaining margin as well as total cost; 30M supplies ample margin once those inequalities are formalized. Authorization preprocessing is empty for SYSTEM and the installed target requires no account creation. Current constants are code-level constants, not future mutable pricing guarantees.

## Outer reference rules and remaining boundary

Prove directly over reference steps: protected-address code/storage framing; actual transfer and no-overflow funding conservation; call-entry/exit and rollback extraction; unique attempted runtime occurrence; execution cost for each LOG0; and an amortized block/history budget respecting both gas pools. These rules must cover type-4 authorization, CLZ/SLOTNUM, SELFDESTRUCT, CREATE, delegation, precompiles, withdrawals and other necessary reference mechanisms, but do not simulate all of them in pinned EVMYul. New opcodes can affect whether/with what values outer code calls the predeploy; they cannot be dropped from admissible histories. Existing NestedEvent tree proofs can guide interface design but do not automatically count reference traces through those differing mechanisms.

Runtime adaptation does not prove constructor installation. The initializer component of PControl needs its own small init-code/collision/code-deposit adapter (including state gas), or an explicitly selected installed checkpoint with justified state. It also does not select reversible/permanent inhibition, empty/nonempty scheduling, upgrade policy, SYSTEM crypto/address assumptions or funding inputs. None is adopted here.

No source-level counterexample was found to the restricted successful-runtime shadow-gas approach. Three naive versions do fail: exact full-log equality on paid transfers; shadow-success correspondence required for actual OOG; and arbitrary finite trace implying a representable UInt256 shadow budget. The interfaces above explicitly avoid those claims.
